# 基本方針

Domain ModelはMVPで必要な概念とルールを中心に設計します。

将来利用する可能性だけを理由にEntity、Value Object、状態、振る舞いを追加しないでください。

Domain層はInfrastructureに依存させません。

特に以下をDomainへ持ち込まないでください。

- Diesel
- PostgreSQL
- HTTP framework
- 認証Provider
- Token
- 環境変数

本サービスでは、主なDomain概念を以下のように整理します。

1. `Source` = どこから得た情報か
2. `Practice` = 実際に試せる方法
3. `Experience` = それを試した体験

# Practice

サービス上で紹介する「実際に試せる方法」を表します。

いわゆるライフハックだけに限定せず、短時間で実践できる方法を幅広く対象とします。

例えば、

- 学習方法
- 仕事や家事の工夫
- 気分転換
- 頭の体操
- 健康や生活改善に関する実践

などを含みます。

PracticeはSourceとは独立した概念です。

1つのSourceから複数のPracticeが得られることもあり、1つのPracticeが複数のSourceによって紹介・裏付けられることもあります。

そのため、`Practice`と`Source`はN:Mの関係とします。

# Source

Practiceの根拠・出典となる情報源を表します。

例：

- Web記事
- 動画
- SNS投稿
- その他のWebコンテンツ

Sourceを識別するURLは`SourceUrl`としてDomain上で表現することを検討してください。

単なる`String`として無制限に扱わず、少なくとも以下を防いでください。

- 空文字
- URLとして明らかに不正な値

ただし、URL正規化について独自仕様を過剰に実装しないでください。

例えば、

```text
https://example.com/article
https://example.com/article/
```

を同一URLと判断するかは現時点では未確定です。

要件として決まっていないURL正規化を推測して実装しないでください。

# Experience

ユーザーがPracticeを実際に試した体験を表します。

Experienceには任意で短い補足コメントを持てます。

## ExperienceNote

`ExperienceNote`はValue Objectとして表現することを検討してください。

制約は以下です。

- 任意
- 最大100文字
- URLは禁止
- Markdownは扱わない
- 画像添付は扱わない
- 長文レビュー用途にはしない

URL判定に高度な自然言語解析は必要ありません。

どの文字列をURLとして拒否するのかが、実装とテストから理解できるようにしてください。

投稿者は自身のExperienceを更新できることを想定します。

将来的には、運営が問題のあるExperienceNoteを非表示にできる可能性がありますが、現時点で必要以上にモデリングしないでください。

# ListingRequest

ユーザーが特定のURLについて、

「この情報をサービスへ掲載してほしい」

と依頼するための概念です。

最低限、以下の状態を表現します。

```text
Pending
Accepted
Rejected
```

`ListingRequestStatus`など、Domain上で意味の分かる型として表現してください。

# ListingRequestの重複制約

同一`SourceUrl`に対するListingRequestは複数作成できません。

対象となる状態は、

- Pending
- Accepted
- Rejected

のすべてです。

つまり、一度でも同じ`SourceUrl`についてListingRequestが作られた場合、新しいListingRequestは作成しません。

これはMVPにおける重要な不変条件です。

アプリケーションコードだけでなく、並行実行時にも破壊されにくい永続化設計を採用してください。

# ID

Entity / Aggregateを識別するIDは原則としてUUID version 7を利用します。

例：

- `UserId`
- `PracticeId`
- `SourceId`
- `ExperienceId`
- `ListingRequestId`

DBの連番値をDomain IDとして使用しないでください。

また、可能であればIDごとに型を分け、

```text
PracticeId
SourceId
ExperienceId
```

など異なるIDを誤って渡しにくい設計を優先してください。

# 日時

日時はUTCを基準とします。

Rust内部でもUTCとして扱います。

利用者のタイムゾーンに合わせた表示変換はFrontendの責務です。

PostgreSQL側では原則として`TIMESTAMPTZ`を利用します。

# Aggregate境界

Aggregate境界は、現在のMVP要件と不変条件から設計してください。

単にDB上で関連があることを理由に、大きなAggregateへまとめないでください。

特に、

```text
Practice
Source
Experience
ListingRequest
```

について、それぞれ独立して変更可能なライフサイクルを考慮してください。

採用したAggregate境界とその理由を実装完了時に説明してください。
