# サービスの目的

短時間で試せる実践的な方法を集約し、その出典と実際に試したユーザーの体験を整理するWebサービスを開発します。

対象は、いわゆるライフハックに限定しません。

- マインド・メンタル
- 頭の体操
- 学習
- 仕事
- 家事
- 生活改善
- その他、短時間で試せる実践的な方法

などを幅広く扱います。

世の中にはSNS、動画、Web記事などに「ちょっと試してみたい方法」が数多く存在しますが、情報が媒体ごとに散在しています。

そのため、

- どんな方法なのか
- どのくらい時間がかかるのか
- 元の情報はどこなのか
- 実際に試した人はどう感じたのか

を横断的に確認することが難しくなっています。

このサービスでは、

1. `Source` = どこから得た情報か
2. `Practice` = 実際に試せる方法
3. `Experience` = それを試した体験

として情報を構造化し、集合知として蓄積します。

```text
Source
  ↓
Practice
  ↓
Experience
```

単なるリンク集や記事まとめではなく、**「実際に試せる方法」を中心に整理し、その後の体験までつなげること**を重視します。

# MVPの基本フロー

MVPでは、ユーザーが自由にPracticeを登録する方式にはしません。

ユーザーは掲載してほしい情報のURLを運営へリクエストします。

```text
ユーザー
  ↓
URLを掲載リクエスト
  ↓
運営が内容を確認
  ↓
Source / Practiceを登録
  ↓
サービス上に掲載
```

情報品質を担保するため、SourceやPracticeの登録は当面運営側で行います。

# MVPで提供する主な機能

MVPでは、主に以下を扱います。

- Practiceの閲覧
- PracticeとSourceの紐付け
- ユーザーによる掲載リクエスト
- Practiceを試したExperienceの記録
- Experienceへの短い補足コメント
- 新しく登録されたPracticeの閲覧

レコメンドなど高度な探索機能はMVPでは扱いません。

# 運営方針

MVPでは専用の運営画面は作成しません。

運営作業は当面、PostgreSQLへの直接操作などで対応します。

そのため、MVPでは以下を実装対象外とします。

- Admin UI
- Admin専用API
- Admin認証
- Role Based Access Control

必要性が明確になった段階で追加します。

# 認証

匿名利用可能な既存の認証実装を利用します。

認証方式そのものは本サービスで新規設計しません。

サービスのDomainからは認証ProviderやToken方式を意識せず、ユーザーを識別する必要がある場合のみ`UserId`として扱います。

# MVPで扱わないもの

以下は現時点では対象外です。

- レコメンド
- AIによるPractice生成
- AIによるSource解析
- 自動クロール
- ユーザーによるPractice直接登録
- 長文レビュー
- Markdown投稿
- 画像投稿
- 課金
- 高度な検索
- 高度なURL正規化

将来を予測して先に実装せず、必要性が明確になった段階で検討します。
